# Tool calling

The engine **emits** tool calls and never executes them. Running a function is
the application's job — an inference engine that shells out is a security
problem wearing a feature's clothes.

Everything here works today on Qwen3, in the CLI, in the library and over
HTTP. What is *not* here yet: constrained decoding (`strict` mode), which is
the only way to guarantee a call is well-formed rather than measure how often
it is. See [the measurement](#does-a-06b-actually-do-this) below for what that
costs in practice.

## The shape of it

Three things have to line up, and each is somewhere different:

| | where | what |
|---|---|---|
| schemas in | `src/template.c` | a `# Tools` block in the **system turn**, byte-identical to HF's template |
| the call out | `src/generate.c` | `<tool_call>` / `</tool_call>` are single tokens, so the JSON is routed to its own channel |
| parsing | `src/tools.c` | conservative: a malformed block is reported as malformed, never repaired |

The channel split is the same mechanism that keeps reasoning off stdout, for
the same reason. A client that ignores `tool_calls` must not find the raw JSON
sitting in `content`, because the next stage in this pipeline is a TTS engine
and it would read the function call out loud.

## CLI

```sh
mynah-slm run -m models-local/Qwen3-0.6B-Q4_K_M.gguf \
              --tools tools.json -p "What is the weather in Verona?"
```

`tools.json` is an OpenAI-shaped array. The `parameters` schema is passed
through **verbatim** — it is your text, and re-serializing it would only move
the prompt away from what the model was trained on:

```json
[{"type": "function",
  "function": {"name": "get_weather",
               "description": "Get the current weather in a given city",
               "parameters": {"type": "object",
                              "properties": {"city": {"type": "string"}},
                              "required": ["city"]}}}]
```

The answer text goes to stdout as usual; a call is one extra JSON line, so
both halves stay machine-readable:

```
{"tool_calls":[{"index":0,"id":"call_0","type":"function","function":{"name":"get_weather","arguments":"{\"city\": \"Verona\"}"}}]}
```

A block the model emitted but mangled is counted and reported on **stderr**
(`1 malformed tool call discarded`), never silently dropped and never guessed
at. A caller executes these.

## HTTP

`POST /v1/chat/completions` takes `tools` and `tool_choice` and answers in
OpenAI's shape: `finish_reason: "tool_calls"`, the calls in
`message.tool_calls`, `content` set to `null` when the turn was only a call.
On SSE the call arrives as **one** delta — half a JSON object is not a partial
answer, it is something a client could act on wrongly.

`tool_choice` supports `"none"` (don't put the schemas in the prompt at all)
and `"auto"` (the default). `"required"` is accepted but **not enforced**:
forcing a call needs constrained decoding, and pretending otherwise would be a
lie the client only discovers in production.

The second turn works the way you'd expect — send the assistant turn with its
`tool_calls` and then a `tool` message with the result. Both are replayed into
the prompt; a model that cannot see its own call cannot make sense of the
result that follows it. Multiple `tool` messages in a row become **one** user
turn with several `<tool_response>` blocks, which is what the template
specifies and what makes parallel calls come back correctly.

## Library

```c
mynah_slm_tool_set *tools = mynah_slm_tools_parse(json, len, err, sizeof err);

mynah_slm_render_chat_tools(msgs, n, mynah_slm_tools_items(tools),
                            mynah_slm_tools_count(tools), think, buf, cap);

gp.tool_open  = mynah_slm_token_find(tok, "<tool_call>");
gp.tool_close = mynah_slm_token_find(tok, "</tool_call>");
gp.cb_tool    = my_collector;      /* NULL discards the channel */

mynah_slm_tool_call calls[8];
size_t blocks = 0;
long n = mynah_slm_tool_calls_parse(text, len, calls, 8, &blocks);
/* n < blocks means the model produced JSON we refused to repair. */
```

Markers are resolved **by name**, never by id: a hardcoded id is right for
exactly one vocabulary. Use `mynah_slm_gen_params_init()` rather than brace
initialization — a marker field left at `0` is a real token id, not "unset".

## What is pinned by tests

`tests/test_tools.c` needs no checkpoint and runs in CI:

- ten renderings compared **byte for byte** against HF's
  `apply_chat_template`, including the schema spacing, a tool with no
  description or parameters, the full call → result round trip, parallel calls,
  and text plus a call in one turn. The fixture is generated by
  `tools/gen_chat_fixture.py` and committed;
- the parser against the ways a model gets it wrong: truncated JSON, a missing
  name, scalar arguments, a brace inside a string, prose containing `{`, one
  good call next to a broken one.

`tests/test_server.sh` covers the wire: `finish_reason`, the call staying out
of `content`, `tool_choice: "none"`, the second turn, and SSE.

## Does a 0.6B actually do this?

Rendering a schema and parsing a call are solved problems. Whether a 600M
model *decides* correctly is not, and the failure that matters does not look
like a failure: instead of calling `get_weather`, the model cheerfully invents
the weather. That is a perfectly well-formed answer and it is wrong.

`tools/eval/tool_calls.py` scores that decision, per language, on the real
binary:

```sh
cd tools && uv run python -m eval.tool_calls ../models-local/Qwen3-0.6B-Q4_K_M.gguf
```

Every case scores three things separately — did it call at all, was it the
right function, were the arguments right — and half the suite is prompts that
must **not** produce a call, because a model that invokes a function to say
hello is as broken as one that never invokes anything.

### Measured, 2026-08-07

`Qwen3-0.6B-Q4_K_M`, staged locally, M-series Mac, 8 threads, greedy
(`--temp 0`), 30 prompts across 7 languages, 4 tools.

| | `--think off` | `--think on` |
|---|---|---|
| correct | **21/30 (70%)** | **26/30 (87%)** |
| answered instead of calling | 9 | 2 |
| called a tool for a chat turn | 0 | 1 |
| wrong function or arguments | 0 | 1 |
| JSON we could not parse | **0/30** | **0/30** |
| seconds per turn | ~17 | ~22 |

Per language, thinking on: de 4/4 · en 7/8 · es 3/4 · fr 3/4 · it 7/8 · nl 1/1
· pt 1/1.

**Thinking is what makes tool calling work on a model this small.** Not a
tuning preference — a 17-point swing, and it removes the failure mode that
matters. The cost is about five seconds a turn on this machine.

**The failure has one shape, and it is not malformed JSON.** With thinking off,
eight of the nine misses were the same tool: asked for the weather while
holding a `get_weather` function, the model answers from its own parameters
instead of calling. One English case managed *"I don't have access to real-time
weather data, but I can tell you that the weather in Berlin is currently
cloudy"* — self-contradictory, well-formed, and completely wrong. That is the
danger of a small model with tools: the failure looks like a good answer.
Turning thinking on fixed every one of them; the model reasons about which tool
applies before committing.

Syntax was never the problem. **60/60 turns produced JSON we could parse**, and
the model never invented a function name that did not exist. So `strict` mode —
constrained decoding — would buy us very little here: it fixes the failure this
model does not have. What would help is the decision, and thinking already
moves that.

The four remaining misses, honestly: Italian "Sta piovendo a Berlino adesso?"
still answers in prose; Spanish "Pon un temporizador" does too; a haiku request
spuriously called `set_timer`; and French "Quel temps fait-il à Vérone ?"
called the right function with `city="Verone"` — the accent dropped. That last
one is scored as a failure on purpose. A real geocoding API may well reject it,
and a suite that quietly normalizes away the model's output is a suite that
stops noticing.

### What this means for the pipeline

- Tool calling on a 0.6B is **usable with thinking on**, and roughly a coin
  flip on the weather-shaped cases without it.
- Reasoning stays off the answer channel either way, so `--think on` costs
  latency, never a leak into TTS.
- Re-run this suite before claiming anything about a new model or a new quant.
  It drives the CLI, so it scores whatever the engine can load.
